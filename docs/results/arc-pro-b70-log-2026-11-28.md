## 2. Measured and not kept

- **IGC's built-in math** (OpenCL.std) instead of OpenCuda's functions:
  beyond the CUDA Math API bounds (expf 2.54 ulp, tanhf 4.84, sin 3.38 against
  2) and mostly slower (exp 0.24x).
- **Approximate division / square root under `-use_fast_math`**: no measurable
  gain (langevin-cuda 22.6 -> 22.5 s).
- **half -> float with the device's conversion**: llama.cpp tg128 245 -> 354
  t/s, but test-backend-ops failed (MUL_MAT 2671/2724, flash attention NaNs).
  Bisected: the half -> float part alone causes it; right with
  `-cl-opt-disable`, wrong with IGC 2.42 too, and with two other loop-free
  integer forms of the same conversion (each bit-exact in
  `rt_half_convert`). Not a register-file effect (128 / 256 GRF the same);
  20 IGC debug keys tried had no effect. Kept the integer code.

## 3. Output cross-check and two compiler bugs

`tools/bench/hecbench_xcheck.py` compares the numbers two runs print,
timings left out. OpenCuda against chipStar over the 252 programs both run:
221 the same, 10 without numbers, 21 different; two of those were OpenCuda
errors, both found to be compiler problems:

- **segsort-cuda** (a third of the keys wrong, nondeterministically).
  Bisected over OpenCuda's steps: right with `OCU_SPV_INFER=0`; within it the
  `infer-address-spaces` pass (opt-bisect: one function, `bb_bin_histo`). A
  constant `getelementptr (i8, @shared_array, byte offset)` used directly by
  an instruction (here `atomicrmw`) came out of LLVM 23's SPIR-V back end as
  an access chain whose index is wrong; the same getelementptr as an
  instruction is right. Workaround in cu2spv (`local_const_geps`);
  `rt_shared_atomics` fails 512 of 17408 checks without it. A minimal IR
  reproducer for an upstream report is not found yet (two small modules
  compile right).
- **lrn-cuda** (checksums 0.0025 / 0 against 0.005 / 0.500008). Right with
  `OCU_SPV_DIV64=0` or `-cl-opt-disable`: IGC 2.41 compiled the 64-bit
  division shortcut wrongly in the form `lshr 31` then `== 0`. The test is
  now one unsigned compare; `rt_div64` (1.5 M checks) added.

## 5. Why HeCBench programs do not build

`tools/bench/hecbench_buildfail.py` on the 153 OpenCuda build failures of the
full run (toolkit 4f9930a): Thrust 19 (chipStar builds none of them); 29 fail
for both toolchains because the harness copies one folder and the Makefile
needs files or rules from sibling folders; 11 build with chipStar and not
with OpenCuda. Rebuilt with today's toolkit and the sibling folders linked,
17 of 22 such programs build; left: `clock()`, `__managed__`, `half` from
`cuda_fp16.h` in a `wmma` program, system-scope atomics, a const pointer
cast in `cudaMalloc`.

## 7. Continuous integration

The repository is public; the four workflows now run on pushes to main and
on pull requests. The first runs found: the macOS 14 runner image is gone
(now macOS 15); Ubuntu 24.04's Clang 18 cannot take GCC 14's `<limits>` in a
CUDA device pass (now clang-19 is installed); MinGW-w64 has its own
`__signbitf`; UBSan found two undefined behaviours in tests. Windows passes;
the others are being fixed.

## 8. GPU hang (11:06) and Mi:dm 2.0 training check

Goal: whether Mi:dm 2.0 Mini (2.3B, `LlamaForCausalLM`) can be fully
fine-tuned on one B70 with PyTorch XPU (no OpenCuda), for a code-specialised
model. Memory estimate: mixed precision (fp32 weights and gradients, bf16
compute, 8-bit AdamW) about 23 GB plus activations, so feasible; pure bf16
would lose small updates to rounding; Base (11.5B) needs over 46 GB for
weights and gradients alone, so LoRA only on one GPU.

It could not be measured: from 11:06 the GPU stopped working for every
program. The driver recorded a GPU hang (`devcoredump` created 11:06:04, a
new one 11:49:56 after a probe). Allocations still succeed, but filling
device memory, copying more than about 1 MiB to the GPU, and loading any
model fail (`UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY` / `OUT_OF_RESOURCES`),
also for OpenCuda (`rt_mem` 42/49 against 49/49 in the morning) and for the
QLoRA script that trained Qwen3-4B correctly on 2026-11-25, run in a clean
environment without OpenCuda. PCIe link (5.0 x16 to the card) and memlock
limit (unchanged since July) are not the cause. At 11:06 a PyTorch LoRA test
and the HeCBench rerun shared the GPU, after several GPU processes had been
killed during work; which of these triggered the hang needs the dump, which
only root can read. Recovery needs root (rebinding the xe driver for the
device, or a power cycle).

Lessons applied from here on: one GPU job at a time, no automatic resume,
and letting GPU programs end instead of killing them.
