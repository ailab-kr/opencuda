# 실험 기록, 2026-11-28 (Intel Arc Pro B70)

[English](arc-pro-b70-log-2026-11-28.md) · **한국어**

2026-11-28에 Arc Pro B70에서 해 본 것, 잰 것, 채택한 것과 채택하지 않은 것. 요약 수치는 [arc-pro-b70.ko.md](arc-pro-b70.ko.md)에도 있고, 각 변경의 이유는 커밋 메시지와 카드에 있다. 시각은 UTC. 시험 묶음에 들어가지 않은 실험 스크립트는 [experiments/2026-11-28](experiments/2026-11-28/)에 있다.

## 2. 재고 채택하지 않은 것

- **IGC 내장 수학 함수**(OpenCL.std): CUDA Math API 한도를 넘고(expf 2.54 ulp, tanhf 4.84, sin 3.38, 한도 2) 대부분 더 느림(exp 0.24배).
- **`-use_fast_math`에서 근사 나눗셈·제곱근**: 의미 있는 이득 없음(langevin-cuda 22.6 → 22.5초).
- **half → float를 장치 자체 변환으로**: llama.cpp tg128 245 → 354 t/s였지만 test-backend-ops가 틀림(MUL_MAT 2671/2724, flash attention NaN). 쪼개 보니 half → float 부분만으로 생기고, `-cl-opt-disable`이면 맞고, IGC 2.42에서도 틀리고, 같은 변환을 반복 없는 정수 코드 두 가지로 써도 틀림(각각은 `rt_half_convert`에서 비트까지 맞음). 레지스터 파일 문제는 아님(128·256 GRF 같음). IGC 디버그 키 20개는 효과 없음. 정수 코드를 유지.

## 3. 출력 교차 확인과 컴파일러 오류 두 건

`tools/bench/hecbench_xcheck.py`는 두 실행이 찍은 숫자를 시간 값을 빼고 비교한다. 두 도구가 모두 끝까지 돌린 252개에서 OpenCuda와 chipStar는 221개 같음, 10개 숫자 없음, 21개 다름. 그중 둘이 OpenCuda의 오류였고, 둘 다 컴파일러 문제로 밝혀졌다.

- **segsort-cuda**(키의 약 1/3이 틀림, 실행마다 다름): OpenCuda 단계를 하나씩 끄니 `OCU_SPV_INFER=0`이면 맞고, 그 안에서는 `infer-address-spaces` 패스였다(opt-bisect: 함수 하나, `bb_bin_histo`). 명령어가 바로 쓰는(여기서는 `atomicrmw`) 상수 `getelementptr (i8, @shared 배열, 바이트 오프셋)`를 LLVM 23의 SPIR-V 백엔드가 인덱스가 틀린 access chain으로 내보냈다. 같은 getelementptr가 명령어이면 맞다. cu2spv에서 우회(`local_const_geps`). 우회가 없으면 `rt_shared_atomics`가 17408건 중 512건 틀린다. 상류 보고용 최소 IR 재현은 아직 못 만들었다(작은 모듈 두 개는 바르게 나온다).
- **lrn-cuda**(체크섬 0.0025 / 0 대 0.005 / 0.500008): `OCU_SPV_DIV64=0`이나 `-cl-opt-disable`이면 맞음. IGC 2.41이 64비트 나눗셈 지름길의 `lshr 31` 뒤 `== 0` 꼴을 틀리게 컴파일했다. 검사를 부호 없는 비교 하나로 바꿨고 `rt_div64`(150만 건)를 더했다.

드라이버 캐시(llama.cpp는 156MB)가 이미 두 번째 시작부터 빠르게 한다. 그동안의 400초 대기는 바이너리를 새로 빌드해서였다. 미리 빌드는 그 실행이 쓰지 않는 모듈도 컴파일한다(캐시 408MB).

## 5. HeCBench 프로그램이 빌드되지 않는 이유

전체 실행(툴킷 4f9930a)의 OpenCuda 빌드 실패 153개에 `tools/bench/hecbench_buildfail.py`: Thrust 19개(chipStar도 하나도 못 함), 측정 스크립트가 폴더 하나만 복사하는데 Makefile이 옆 폴더의 파일·규칙을 쓰는 것 29개(두 도구 모두 실패), chipStar는 빌드하고 OpenCuda는 못 하는 것 11개. 오늘 툴킷으로 옆 폴더를 이어 붙이고 다시 빌드하니 그런 22개 중 17개가 빌드된다. 남은 것: `clock()`, `__managed__`, `wmma` 프로그램의 `cuda_fp16.h` `half`, system-scope atomic, `cudaMalloc`의 const 포인터 변환.

## 6. 오늘 툴킷으로 HeCBench 다시 돌리기(미완)

09:35에 417개로 시작(먼저 전체 실행에서 fail·crash·timeout이던 91개). 11:14에 멈출 때 79개 완료(crash 51, timeout 14, fail 10, pass 3, ran 1. crash는 전체 실행처럼 대부분 입력 파일이나 Python 모듈이 없어서). 아직 비교할 수 없고, 이어서 돌릴 예정. 11:03–11:14에는 PyTorch 작업(8절)과 동시에 돌았다. "GPU 하나에 작업 하나"라는 측정 규칙을 어긴 것이다.

## 7. 지속적 통합(CI)

저장소가 공개되어, 네 워크플로가 이제 main 푸시와 PR마다 돈다. 첫 실행에서 찾은 것: macOS 14 러너 이미지가 없어짐(이제 macOS 15), Ubuntu 24.04의 Clang 18이 CUDA 장치 컴파일에서 GCC 14의 `<limits>`를 받지 못함(이제 clang-19 설치), MinGW-w64에 자체 `__signbitf`가 있음, UBSan이 시험 코드의 정의되지 않은 동작 두 곳을 찾음. Windows는 통과, 나머지는 고치는 중.

## 8. GPU 행(11:06)과 믿음 2.0 학습 확인

목표: 믿음 2.0 Mini(2.3B, `LlamaForCausalLM`)를 B70 한 장에서 PyTorch XPU로(OpenCuda 없이) 풀 파인튜닝해 코딩 특화 모델을 만들 수 있는가. 메모리 추정: 혼합 정밀도(fp32 가중치·기울기, bf16 계산, 8-bit AdamW) 약 23GB에 활성값이 더해지므로 가능. 순수 bf16은 작은 갱신이 반올림으로 사라질 수 있음. Base(11.5B)는 가중치·기울기만 46GB가 넘어 GPU 한 장으로는 LoRA만 가능.

측정은 하지 못했다. 11:06부터 GPU가 모든 프로그램에서 동작하지 않는다. 드라이버가 GPU 행을 기록했다(`devcoredump` 11:06:04 생성, 시험 뒤 11:49:56에 새로 생성). 할당은 성공하지만, 장치 메모리 채우기, 약 1MiB 넘는 GPU 쪽 복사, 모델 불러오기가 모두 실패한다(`UR_RESULT_ERROR_OUT_OF_DEVICE_MEMORY` / `OUT_OF_RESOURCES`). OpenCuda(`rt_mem` 42/49, 오전에는 49/49)에서도, 2026-11-25에 Qwen3-4B를 바르게 학습시킨 QLoRA 스크립트를 OpenCuda 없는 깨끗한 환경에서 돌려도 같다. PCIe 연결(카드까지 5.0 x16)과 memlock 한도(7월 이후 그대로)는 원인이 아니다. 11:06에는 PyTorch LoRA 시험과 HeCBench 재실행이 GPU를 함께 쓰고 있었고, 그 전에 작업 중인 GPU 프로세스를 여러 번 강제 종료했다. 어느 것이 행을 일으켰는지는 root만 읽을 수 있는 덤프가 있어야 안다. 복구에는 root가 필요하다(해당 장치의 xe 드라이버 재연결 또는 전원 재시작).

이제부터 지키는 것: GPU 작업은 한 번에 하나, 자동 재개 없음, GPU 프로그램은 죽이지 않고 끝나기를 기다림.
