# 거버넌스

[English](GOVERNANCE.md) · **한국어**

> 검토용 초안. 대괄호 항목(`[...]`)은 아직 정하지 않은 결정이다.

## 1. 목적

OpenCuda는 백엔드를 제공하는 칩이라면 어떤 칩에서든 CUDA C++ 프로그램을 돌리게 하고,
각 칩이 얼마나 잘 돌리는지 공개된 벤더 중립 시험으로 재기 위해 존재한다.
OpenCuda는 모두가 함께 쓰는 기반 시설이다. 기여자의 소속 회사를 포함해 어떤 벤더도 단독으로 좌우하지 못한다.

## 2. 운영 주체

OpenCuda는 중립적인 비영리 단체 [운영 주체의 이름, 추후 결정]가 맡아 운영한다. 이 주체는 다음을 한다.

- 프로젝트 이름, 도메인, 상표, 그리고 선택한 라이선스가 요구하는 만큼 기여자가 주는 저작권 양도나 사용 허락을 보유한다.
- 아래 절차를 넘어서는 기술 결정을 지시하지 않는다.
- 재정과 프로젝트를 후원하는 단체의 목록을 공개한다.
- 후원자가 적합성 결과에 영향을 줄 수 있는 조건으로는 자금이나 현물 지원을 받지 않는다.

## 3. 역할

| 역할 | 누가 | 할 수 있는 일 |
|---|---|---|
| 기여자 | 누구나 | 이슈, 풀 리퀘스트, RFC 제안을 올린다 |
| 검토자 | 유익한 검토 이력이 있는 기여자 | 한 영역의 변경을 승인한다 |
| 관리자 | 관리자들이 임명한다(아래) | 병합, 출시, RFC 투표 |
| 백엔드 관리자 | 백엔드의 벤더나 커뮤니티가 추천한 사람 | `backends/<이름>/` 안의 변경만 병합한다 |
| 운영위원회 | 비영리 단체의 이사 | 법무, 재정, 상표, 행동 강령 이의 신청 |

관리자는 지속적인 기여를 바탕으로 현 관리자의 3분의 2 찬성으로 임명한다.
같은 조직에 속한 관리자는 [3분의 1]을 넘을 수 없다. 어떤 변경이 이 한도를 깨게 되면
그 조직 출신의 신규 임명을 잠시 멈춘다. 12개월 동안 활동이 없는 관리자는 명예 관리자로 옮긴다.
관리자는 자기 소속 회사의 백엔드나 제품에 관한 결정에서 이해 충돌을 밝히고 그 표결에서 기권한다.

## 4. 의사 결정

- 일상적인 변경: 풀 리퀘스트, 관리자 한 명의 승인, 검사 통과, 그리고 영업일 [3]일 뒤에도 해소되지 않은 반대가 없을 것.
- 백엔드 인터페이스(`ocu_backend.h`), 결과 기록 형식, 점수 규칙, 허용 오차를 건드리는 것은 모두 RFC를 거친다.
- 묵시적 합의로 풀리지 않는 분쟁은 관리자 단순 과반수로 정한다. RFC는 3분의 2 과반이 필요하다.
- 운영위원회는 위 표에 적힌 사안만 결정한다.

### 시험과 구현은 분리한다

한 변경은 적합성 시험 경로와 구현 경로 중 하나만 건드릴 수 있고 둘 다 건드릴 수 없다.
한 기능의 시험과 구현은 서로 다른 사람이 쓰는 것이 좋다.
시험이 틀려 보이면 이의를 기록하고 검토한다. 구현 쪽에서 시험을 고치지 않는다.
이것이 벤더 사이에서 시험의 중립성을 지킨다.

## 5. RFC 절차

1. `RFC: <요약>`이라는 제목으로 이슈를 열고, 틀에 따라 `rfcs/` 아래에 문서를 추가한다.
   틀의 항목은 동기, 설계, 기존 백엔드에 미치는 영향, 적합성에 미치는 영향, 대안, 미해결 질문이다.
2. 토론은 최소 [14]일 열어 둔다. 영향받는 백엔드의 백엔드 관리자에게는 의견을 명시적으로 요청한다.
3. 관리자가 한 번 투표하고, 결과와 이유를 RFC에 기록한다.
4. 백엔드 인터페이스를 호환되지 않게 바꾸는 RFC가 승인되면 `OCU_BACKEND_ABI`를 올리고,
   이전 버전을 적어도 [한 번의 출시] 동안 불러올 수 있게 둔다.
5. 구현은 RFC를 인용하는 일반 풀 리퀘스트로 이어진다.

## 6. 백엔드 승인 기준 (벤더 중립)

백엔드는 다음을 만족할 때 주 트리에 들어온다.

1. 현재 ABI의 필수 항목을 모두 구현하고, 지원하지 않거나 끝나지 않은 기능을 성공이 아닌 그대로 보고한다.
2. 공개 소스와 공개 문서로 빌드된다. 빌드에 필요한 독점 파일이 없어야 한다.
   드라이버나 라이브러리에 실행 중에 의존하는 것은 허용되며, 문서화해야 한다.
3. BACKEND_GUIDE.ko.md의 백엔드 수준 중 B0(실행 지원을 주장하면 B1도)를 실제 하드웨어에서 통과하고,
   다른 사람이 설명할 수 있는 기계(장치, 드라이버, 운영체제)에서 얻은 결과 기록을 첨부한다.
4. 장치 코드 이미지 형식과 그 이미지를 만드는 방법을 문서화한다.
5. 이름이 밝혀진 백엔드 관리자가 적어도 [2]명 있고, 그중 한 명 이상은 프로젝트의 공개 채널로 연락이 닿는다.
6. 코드가 프로젝트의 라이선스를 따르며, 다른 모든 코드와 같은 조건으로 기여된다.

같은 기준을 모든 벤더에 적용한다. 이 기준은 벤더의 순위를 매기지 않고, 어떤 상업적 약정도 요구하지 않으며,
하드웨어 기증도 요구하지 않는다(다만 지속적 시험용 하드웨어는 환영하며, 운영 주체가 결과에 영향이 없게 처리한다).

제거: 12개월 동안 관리자가 없거나, 계획 없이 두 번 연속 출시에서 주장한 수준을 통과하지 못하는 백엔드는
통지 후 `attic/` 영역으로 옮긴다.

## 7. 적합성 결과

- 점수는 공개 시험을 공개적이고 재현 가능한 방식으로 돌려 얻는다. 비공개 시험 세트의 결과는 프로젝트 결과로 발표하지 않는다.
- 누구나 결과 기록을 제출할 수 있다. 제출물은 가능하면 다시 돌려 확인하고, 그렇지 않으면 미검증으로 표시한다.
- 벤더는 자기 결과에 의견을 달 수 있지만 고칠 수는 없다.
- 발표된 결과는 시험이나 기록의 오류 때문에만 바꾸며, 정정 내용은 이력에 보이게 남긴다.
